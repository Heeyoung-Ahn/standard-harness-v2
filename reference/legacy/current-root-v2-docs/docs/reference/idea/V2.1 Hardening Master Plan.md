## Executive Decision

V2.1 hardening should finish the release-readiness gaps discovered after XP-10A before expanding the product operating model.

The V2.1 scope should include:

1. Release evidence integrity.
2. Security boundary and policy-root hardening.
3. HR-200 metric evidence hardening.
4. Review governance as a release-blocking evidence gate.
5. Wiki knowledge architecture as a projection-only navigation layer.
6. Executable release validation.
7. Minimal maintainability hardening needed to keep V2.1 operable.

The V2.1 scope should defer to V2.2:

1. Requirements interview and PRD writing.
2. Feature tree and flow modeling.
3. Requirement candidate normalization.
4. Wireframe projection.
5. UI module and design mockup contracts.
6. Portfolio/workstream/release-train operating layers.

## Current Preflight Requirement

Before starting any new hardening XP:

```powershell
git status --short
python -m unittest discover -s tests
```

The working tree must be clean. Local generated state such as `.harness/state/harness.sqlite3` must be moved outside the repository before baseline regression. If baseline regression fails or hangs, stop and report before mixing baseline repair with the next hardening XP.

## Master Execution Order

### 0. Preflight Hygiene

Purpose: make the branch safe for new hardening work.

Required actions:

- Move `.harness/state/harness.sqlite3` outside the repository when present.
- Commit or remove unrelated `docs/reference/idea/**` notes before implementation branches.
- Confirm `git status --short` is clean.
- Confirm `python -m unittest discover -s tests` passes.

Output: clean baseline for the first new hardening branch.

### 1. XP-10B Release Evidence Integrity

Purpose: prevent release evidence from making false pass claims.

Scope:

- Replace placeholder `reviewedCommit` values such as `pending-xp-10a` with real commit hashes.
- Make challenge/review evidence validators verify that `reviewedCommit` is a real git commit object.
- Record full regression as structured evidence with command, result, duration, log path, timeout status, and last test.
- Make V2.1 conformance verify regression evidence.
- Remove the hardcoded `HR-130R` partial-coverage escape hatch or replace it with explicit policy-backed non-applicability.
- Preserve the generated-state invariant: repo-root `.harness/state/harness.sqlite3` must not remain after release validation/regression.

Representative tests:

- Placeholder reviewed commit blocks release.
- Invalid reviewed commit blocks release.
- Missing full regression evidence blocks release.
- HR-130R partial coverage blocks release.
- Generated repo-local SQLite state fails hygiene checks.

Recommended branch:

```text
codex/v21-xp-10b-release-evidence
```

### 2. XP-SecurityA Boundary And Policy Root Hardening

Purpose: close the concrete security bypasses found during adversarial review.

Scope:

- Replace `Path.cwd()` policy loading with explicit canonical repo/store root resolution.
- Separate `repo_root`, `state_root`, `execution_cwd`, and `artifact_root`.
- Reject internal `..` path traversal in boundary normalization.
- Prevent Wiki applier path traversal outside `_ops/wiki`.
- Prevent evidence trust spoofing through caller-supplied trusted statuses.
- Reject tracked symlink escape in release archive creation.
- Validate challenge/review artifact identifiers before path construction.

Representative tests:

- SECRET evidence registration cannot be bypassed by changing cwd.
- `src/../_harness/...` cannot bypass product packet boundary rules.
- Wiki targetPage traversal cannot write outside `_ops/wiki`.
- Forged `TRUSTED_CI` evidence cannot close a packet.
- Release archive rejects symlink escape.

Recommended branch:

```text
codex/v21-securitya-boundary-policy-root
```

### 3. XP-MetricsA HR-200 Evidence Hardening

Purpose: make HR-200 metrics reliable release evidence instead of shape-only metrics.

Scope:

- Remove undefined trust statuses such as `TRUSTED` from metric logic and tests.
- Reuse `EvidenceTrustPolicy` statuses for trusted evidence ratio calculation.
- Link `sourceWatermark` to input record range, hash, generation command, and generated-at timestamp.
- Avoid defaulting meaningful release metrics to perfect `1.0` when no source records exist unless the metric is explicitly not applicable.
- Make stale or incomplete HR-200 metrics block conformance.

Representative tests:

- `REPRODUCED_BY_HARNESS` and `TRUSTED_CI` count as trusted evidence.
- `MANUAL_ONLY` does not count as trusted evidence.
- Missing source records or stale source watermark blocks release.
- Invalid ratio types block release.

Recommended branch:

```text
codex/v21-metricsa-hr200-evidence
```

### 4. XP-10C Review Governance Gate

Purpose: promote implementation review from informal Markdown into a formal closeout/release-blocking evidence gate.

Scope:

- Review profile policy.
- Review bundle schema.
- Review finding schema.
- Evidence integrity validator.
- Final adjudication validator.
- Release self-test validator.
- Packet closeout and V2.1 release validation integration.

Required behavior:

- Missing required review fails.
- Missing or fake reviewed commit fails.
- Stale review evidence fails or emits a stale diagnostic.
- Missing focused test log fails.
- Missing regression evidence for release-bound packet fails.
- Unresolved P0 finding fails.
- Unresolved P1 finding requires accepted risk and final adjudication.
- Conditional pass without final adjudication fails.
- AI review alone cannot release; deterministic evidence and final adjudication are required.

Recommended branch:

```text
codex/v21-xp-10c-review-governance
```

### 5. XP-05B Wiki Knowledge Architecture

Purpose: strengthen long-term memory while preserving projection-only authority.

Scope:

- Wiki page standard skeleton.
- Source tier and authority label.
- Provenance footer model.
- Freshness, owner, and review status.
- Skill-facing index as navigation projection only.
- Mapping-based co-location freshness validation.
- Wiki-related friction/metric signal behavior.
- Projection-only authority boundary for Wiki/reference pages.

Required behavior:

- Wiki/reference pages cannot override requirements, policies, schemas, validators, gate results, trusted evidence, or human decision records.
- Wiki pages claiming `current` must cite canonical sources and evidence.
- Skill-facing index may guide reading order but cannot grant permission, skill execution authority, or release authority.
- Stale wiki references, missing provenance, and failed trusted-context validation emit defined friction signals.

Recommended branch:

```text
codex/v21-xp-05b-wiki-knowledge
```

### 6. XP-ReleaseA Executable Release Gate

Purpose: make `validate --release` execute release-blocking behavior, not only catalog metadata checks.

Scope:

- Define a common release validator protocol.
- Bind release-blocking validator catalog entries to executable validators.
- Execute a minimum release negative scenario bundle.
- Record gate-result-shaped diagnostics.
- Make `validate --v21-conformance --release` fail when a release-blocking validator is only declared but not behaviorally exercised.

Representative tests:

- Catalog entry with importable implementation but broken behavior fails release.
- Missing negative scenario execution fails release.
- Security, review, wiki, metrics, and release evidence validators are reachable from release validation.

Recommended branch:

```text
codex/v21-releasea-executable-gate
```

### 7. XP-MaintA Maintainability Hardening

Purpose: reduce long-term maintenance risk without reopening V2.1 product scope.

Scope:

- Decide whether `.yaml` artifacts remain JSON-compatible-only or move to real YAML parsing.
- Introduce explicit migration versioning and drift detection.
- Split `cli/main.py` into focused command modules.
- Split `validation/aggregator.py` into focused validation services.
- Strengthen skill router role, priority, conflict, and permission handling.

Recommended branch:

```text
codex/v21-mainta-maintainability
```

## Common Implementation Rules

Every hardening XP must:

- Use a dedicated branch.
- Run and record starting `git status --short`.
- Run and record baseline `python -m unittest discover -s tests`.
- Stop if unrelated dirty files exist.
- Stop if baseline regression fails or hangs.
- Write focused tests first and confirm RED where behavior changes are required.
- Implement minimal code/policy/schema/docs.
- Update HR coverage and traceability where applicable.
- Define friction/metric behavior for new gates, validators, evidence paths, wiki paths, handoff paths, or manual commands.
- Run focused tests.
- Run full regression.
- Run V2.1 conformance and release validation when the XP affects release gates.
- Commit only intended files.

Common final checks:

```powershell
python tools\harness_cli.py --json validate --requirements-metadata
python tools\harness_cli.py --json validate --v21-conformance
python tools\harness_cli.py --json validate --release
python tools\harness_cli.py --json validate --all
python tools\run_full_regression.py
python -m unittest discover -s tests
git status --short
```

## Stop Conditions

Stop and report before editing or continuing if:

- Baseline regression fails or hangs.
- `git status --short` contains unrelated dirty files.
- Repo-root generated state remains after cleanup.
- A v1 artifact, `.agents`, `.harness`, plugin, generated state, runtime state, or starter payload would need to be copied or promoted.
- External services, credentials, browser login, network validation, or cloud dependencies are required.
- Markdown, Wiki pages, PRD drafts, generated summaries, mockups, or review notes would become canonical authority.
- Existing V2.1 closed defaults would be changed without an explicit design decision.

## Release Completion Target

V2.1 hardening is complete when:

- Release evidence is tied to real commits and real regression logs.
- Security boundary and policy-root bypasses are blocked by negative tests.
- HR-200 metrics are tied to real trust statuses and source evidence.
- Review governance blocks unresolved findings and fake review evidence.
- Wiki knowledge is projection-only, provenance-backed, and freshness-validated.
- `validate --release` executes behaviorally meaningful release checks.
- Full regression passes from a clean working tree with no repo-local generated state.
